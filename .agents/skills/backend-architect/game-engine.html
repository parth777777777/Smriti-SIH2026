Let’s make the entire V1 pipeline concrete using Memory Match, with actual JSON flowing through each stage.

The key idea is that we should not jump directly from gameplay → score. V1 has several transformations.

Smriti V1 — Complete Flow

PATIENT
   ↓
MEMORY MATCH GAME
   ↓
RAW TELEMETRY
   ↓
FEATURE EXTRACTION
   ↓
FEATURE NORMALIZATION
   ↓
MEMORY DOMAIN SCORE
   ↓
PERSONALIZED BASELINE
   ↓
DEVIATION / Z-SCORE
   ↓
LONGITUDINAL DRIFT DETECTION
   ↓
STATUS / REVIEW FLAG

Let’s walk through one patient session.

1. Game Configuration

Before the game starts, the engine knows what activity is being performed.

{
  "activity_id": "memory_match_v1",
  "primary_domain": "MEMORY",
  "secondary_domains": [],
  "construct": "visual_associative_memory",
  "num_pairs": 4,
  "board_size": "3x3",
  "initial_exposure_ms": 5000
}

This is configuration, not patient data.

The important thing here is that the engine knows:

“This activity is intended to produce a measurement of visual associative memory.”

2. Game Session Begins

Suppose the board contains four pairs:

A A
B B
C C
D D

The actual positions are randomized.

The cards are initially shown for 5 seconds.

Then they are hidden.

The patient starts interacting.

3. Raw Telemetry

This is the most important distinction:

The game should not send "memory_score": 0.72.

The game should simply report what happened.

For example:

{
  "session_id": "sess_001",
  "patient_id": "patient_001",
  "activity_id": "memory_match_v1",

  "started_at": "2026-09-07T19:00:00Z",
  "ended_at": "2026-09-07T19:01:24Z",

  "events": [
    {
      "event": "card_selected",
      "timestamp": 1725735605123,
      "card_id": "card_7",
      "position": 7
    },
    {
      "event": "card_selected",
      "timestamp": 1725735606710,
      "card_id": "card_2",
      "position": 2
    },
    {
      "event": "match_result",
      "timestamp": 1725735606725,
      "card_1": "card_7",
      "card_2": "card_2",
      "is_match": false
    },

    {
      "event": "card_selected",
      "timestamp": 1725735612010,
      "card_id": "card_7",
      "position": 7
    },
    {
      "event": "card_selected",
      "timestamp": 1725735613400,
      "card_id": "card_5",
      "position": 5
    },
    {
      "event": "match_result",
      "timestamp": 1725735613415,
      "card_1": "card_7",
      "card_2": "card_5",
      "is_match": true
    }
  ]
}

This is the raw behavioral record.

We don’t interpret it yet.

4. Why Raw Telemetry Matters

Suppose the patient makes:

7 → 2   WRONG
7 → 5   CORRECT

The engine can later determine:

  • they selected card 7 before

  • they subsequently returned to card 7

  • they eventually found its pair

  • how long they took

  • how many attempts they made

This is much more useful than the game simply saying:

{
  "score": 0.8
}

because we lose the underlying behavioral information.

5. Feature Extraction

Now the Cognitive Engine receives the telemetry.

Its first job is:

Convert raw events into measurable behavioral features.

For example:

{
  "session_id": "sess_001",
  "activity_id": "memory_match_v1",

  "features": {
    "pairs_presented": 4,
    "pairs_recalled": 3,

    "total_attempts": 7,
    "correct_matches": 3,
    "incorrect_matches": 4,

    "accuracy": 0.75,

    "repeated_selections": 2,

    "completion_time_ms": 84000,

    "mean_inter_response_time_ms": 1420
  }
}

Notice what happened.

We went from:

hundreds of raw events

to:

a small set of interpretable measurements

6. What Each Feature Means

For example:

pairs_recalled

3 / 4

The patient successfully found 3 of the 4 pairs.

accuracy

correct matches / total attempts

If:

3 correct
4 incorrect

then:

3 / (3 + 4) = 0.4286

Important: the exact definition of accuracy still needs to be finalized. We shouldn’t casually define it one way in the engine and another way in the game.

repeated_selections

Measures behavior such as:

A → B
...
A → C

where the participant returns to a card/location they have previously encountered.

This may provide information about memory/search efficiency.

But we should be careful about interpreting it as “forgetting.”

completion_time

session_end - session_start

This is useful as an efficiency measure, but it is not automatically a processing-speed measure.

7. Feature Normalization

Now we have raw features like:

{
  "pairs_recalled": 3,
  "accuracy": 0.4286,
  "repeated_selections": 2,
  "completion_time_ms": 84000
}

These are on completely different scales.

So we normalize them.

For example:

{
  "normalized_features": {
    "recall_score": 0.75,
    "accuracy_score": 0.4286,
    "repetition_score": 0.80,
    "efficiency_score": 0.65
  }
}

The exact normalization functions are something we still need to formally design.

For example, a simple bounded transformation could be:

recall_score =
pairs_recalled / pairs_presented

giving:

3 / 4 = 0.75

But completion time is more complicated.

We shouldn’t just say:

score = 1 - completion_time / 100000

without establishing what the reference range means.

A better V1 approach may be to normalize some features relative to the person’s baseline or a calibration distribution.

That’s one of the things we need to settle scientifically.

8. Domain Scoring

Now the normalized features enter the Memory Domain Scorer.

Conceptually:

Normalized Features
        ↓
Memory Scoring Function
        ↓
Memory Domain Score

Example output:

{
  "session_id": "sess_001",
  "domain": "MEMORY",

  "score": 0.68,

  "score_components": {
    "recall": 0.75,
    "accuracy": 0.43,
    "repetition_efficiency": 0.80,
    "temporal_efficiency": 0.65
  }
}

The 0.68 here is illustrative, not a finalized formula.

We still need to determine whether a weighted composite is even the best approach.

For example:

Memory Score =
0.40 × Recall
+ 0.30 × Accuracy
+ 0.15 × Repetition Efficiency
+ 0.15 × Temporal Efficiency

could be one candidate.

But those weights should eventually be justified through validation rather than chosen because they look reasonable.

9. Store the Session Result

Now we have a clean session-level measurement.

{
  "session_id": "sess_001",
  "patient_id": "patient_001",
  "activity_id": "memory_match_v1",

  "domain_scores": {
    "MEMORY": 0.68
  },

  "features": {
    "pairs_recalled": 3,
    "accuracy": 0.4286,
    "repeated_selections": 2,
    "completion_time_ms": 84000
  },

  "valid": true
}

This is what the longitudinal system cares about.

It doesn’t need to repeatedly process every raw card tap when calculating the patient’s historical trend.

10. Building the Personalized Baseline

Suppose the patient plays the game several times during the calibration period.

We might have:

Session 1 → 0.68
Session 2 → 0.74
Session 3 → 0.79
Session 4 → 0.76
Session 5 → 0.81
Session 6 → 0.78
Session 7 → 0.80
Session 8 → 0.82

The system calculates the reference distribution.

For example:

{
  "patient_id": "patient_001",
  "domain": "MEMORY",

  "baseline": {
    "n_sessions": 8,
    "mean": 0.7725,
    "std_dev": 0.046
  }
}

This means:

This individual’s typical Memory Match performance during the reference period was approximately 0.77, with a standard deviation of approximately 0.046.

11. Practice Effects

There’s an important problem here.

The sequence:

0.68
0.74
0.79
0.76
0.81
0.78
0.80
0.82

might not mean the person’s cognition improved.

They may simply have learned how to play Memory Match.

Therefore the baseline system needs to account for practice effects.

For V1, one reasonable engineering approach could be:

Calibration sessions
        ↓
Practice / familiarization
        ↓
Reference baseline

rather than immediately treating Session 1 as representative.

But the exact number of calibration sessions needs to be determined through testing.

12. New Session

Now imagine two weeks later.

The patient completes another Memory Match session.

New score:

0.68

Baseline:

μ = 0.7725
σ = 0.046

We calculate:

Z = (X - μ) / σ

Therefore:

Z = (0.68 - 0.7725) / 0.046

≈

-2.01

So the output could be:

{
  "session_id": "sess_014",
  "domain": "MEMORY",

  "current_score": 0.68,

  "baseline": {
    "mean": 0.7725,
    "std_dev": 0.046
  },

  "deviation": {
    "z_score": -2.01,
    "direction": "BELOW_BASELINE"
  }
}

This does not mean:

“Patient has cognitive decline.”

It means:

“This session’s measured performance is approximately 2 SD below the individual’s reference mean.”

That’s a much more defensible statement.

13. Longitudinal Drift Detection

Now imagine the next sessions produce:

Session 14 → Z = -2.01
Session 15 → Z = -1.72
Session 16 → Z = -1.91
Session 17 → Z = -2.15

Now the system sees something different from a single anomalous session.

It sees:

persistent below-baseline performance

So the longitudinal layer can produce:

{
  "patient_id": "patient_001",
  "domain": "MEMORY",

  "recent_sessions": [
    {
      "session_id": "sess_014",
      "z_score": -2.01
    },
    {
      "session_id": "sess_015",
      "z_score": -1.72
    },
    {
      "session_id": "sess_016",
      "z_score": -1.91
    },
    {
      "session_id": "sess_017",
      "z_score": -2.15
    }
  ],

  "trend": {
    "direction": "DECLINING",
    "persistence": "HIGH"
  },

  "status": "REVIEW_FLAG"
}

Again, REVIEW_FLAG ≠ diagnosis.

It means the system has identified a persistent behavioral-performance deviation that may warrant review.

15. What V1 Has Actually Built

This is important for your SIH explanation.

We’re not just making a Memory Match game.

We’re building this:

                 ┌─────────────────────┐
                 │   MEMORY MATCH      │
                 └──────────┬──────────┘
                            │
                       Raw behavior
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Feature Extraction  │
                 └──────────┬──────────┘
                            │
                    measurable behavior
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Normalization       │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Domain Scoring      │
                 └──────────┬──────────┘
                            │
                       Memory Score
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Personal Baseline   │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Deviation Analysis  │
                 └──────────┬──────────┘
                            │
                            ▼
                 ┌─────────────────────┐
                 │ Longitudinal Engine │
                 └──────────┬──────────┘
                            │
                            ▼
                 Persistent Change Flag

And this is the foundation for V2.

V2 can later take the same pipeline and make the pieces intelligent:

V1
Fixed features
     ↓
Fixed normalization
     ↓
Fixed scoring
     ↓
Statistical baseline
     ↓
Rule-based drift detection


V2
Learned features
     ↓
Personalized normalization
     ↓
Learned domain model
     ↓
Individual trajectory model
     ↓
Adaptive activity selection
     ↓
Confidence-aware longitudinal inference

The critical architectural principle is: the game generates observations; the cognitive engine interprets them. The game itself should never decide that a person is “declining.”
